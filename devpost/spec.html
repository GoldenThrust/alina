How This Works

The browser captures a face image. The backend validates it with OpenCV, calls YouCam Skin Analysis, stores the normalized result in PostgreSQL, and returns the current summary and history to the assistant.

The AI agent coordinates these tools and explains the result without claiming medical certainty.

Core Journey

01 · OpenShow the current skin summary.
02 · CaptureBrowser frame arrives at the backend.
03 · ValidateOpenCV checks face and image quality.
04 · AnalyzeYouCam returns normalized attributes.
05 · InterpretPostgreSQL history drives a recommendation.

Architecture

React + TypeScript

Frontend for the home screen, camera capture, history, conversation, and checkout confirmation.

Node.js + TypeScript

API, OpenCV validation, YouCam client, agent orchestration, and repository layer.

PostgreSQL

Source of truth for scans, attributes, preferences, recommendations, and conversations.

Agent tools

Camera, analysis, history, recommendation, and routine tools exposed through typed contracts.

Data Flow

Browser frame → backend OpenCV validation → YouCam client → PostgreSQL scan record → history comparison → agent summary and recommendation.

External Dependencies

YouCam Skin Analysis
Live API with credential, endpoint, response schema, rate limits, and cost verification required before implementation.
PostgreSQL
Local versioned migrations and Docker Compose setup. The database is the single-user source of truth.
OpenCV
Backend native package handles face detection, alignment, brightness, blur, and frame selection.
Qloo and PayPal
Qloo is required for the normal recommendation path. Credentials, authorization, response contract, availability, and rate limits must be verified before build. The local catalog is a disclosed degraded-mode fallback only.

Failure Modes

  • Camera denied → permission message and retry.
  • OpenCV failure → specific correction and retry.
  • YouCam unavailable → user-friendly retry without storing an incomplete scan.
  • PostgreSQL unavailable → setup message and no incomplete scan.
  • Qloo unavailable or unusable → one retry, then explicitly disclosed local fallback only if the user accepts degraded mode.
  • Insufficient history → current snapshot and four-scan progress cue.
